> **tl;dr** Agent harnesses compact the whole session when the window fills. I think they
> should fold each finished piece of work into a short note the moment it ends, keep the
> full span archived and askable, and fork with the parent's context instead of starting
> subagents from an empty prompt. I built it as a pi package,
> [try it today](#try-it-today). And if this is the kind of problem your team works on, I
> am open to work: [curriculum](/curriculum).

Most of the time when I open a subagent to read its starting prompt, it has the task and
very little of what the parent knew. The parent had spent a while on the problem. It knew
what had already been tried, which guess had been ruled out, which constraint I gave at
the start. The prompt it wrote carries almost none of that, and the child starts figuring
things out from scratch. When it reports back, the report is short, and whatever the child
understood beyond the report stays in a transcript nobody opens.

There are two problems in that:

1. The child started empty, because everything the parent knew had to be written into a
   prompt before the work, by a parent whose main job was never to write that prompt.
2. The parent delegated at all because the "usual" advice for anything log-heavy is "run
   it in a subagent", so the main context does not fill with logs.

The first is a handoff problem. The second is a bloat problem. I think they are two halves
of one missing move.

The case I will use for the whole post is making a project build. The agent runs the
build, reads the log, fixes something, runs again, and repeats until it passes. Most of
what that produces is build and tooling output. What the rest of the session needs from it
is a few lines:

- it builds
- what was changed
- what is still unchecked.

Everything else was useful while the loop was running and is finished now, and it stays in
the context competing for attention with whatever comes next.

<Tangent>
  A task drawn as a list of turns on a main thread. At the build step the agent goes on a
  tangent: it runs the build, reads a 400-line failing log, tries a guess, gets corrected
  by the user, regenerates the API client and builds again. When the build passes, the
  whole tangent collapses into one short note on the main thread, with a handle that
  points back to the archived tangent, and the main thread continues.
</Tangent>

Harnesses deal with that by compacting: when the window is nearly full, summarize what is
there and continue. I think the summarizing should happen when a piece of work finishes,
over that piece of work only, with the full record kept reachable. This post is the
argument for that, and the argument borrows from how people already do it, since, for most
of history, a brain was the only thing that had to manage a small working memory.

The workaround most of us already use says the same thing. Before thinking about any of
this, I used to ask the main agent to write a markdown file with the context and the
reasoning so far, and pass the path to every following subagent, so they all shared one
written brain. It helps a bit. It is also me doing by hand what the harness should be
doing, and the file can only take three shapes:

1. Written once, before the work. It lacks whatever the work reveals.
2. Appended to as the work goes. It grows into a log that every subagent has to read in
   full, most of which has nothing to do with its task. That is the bloat problem moved
   into a file.
3. Rewritten by the agent as it goes, so it always holds the current state. This is the
   best one, and it is close to what this post proposes.

The third shape is a note without a harness behind it. Nothing tells the agent when to
rewrite the file, whatever it drops in a rewrite is gone for good, and there is no thread
behind the file to go back to when the note turns out to be too thin. Those three gaps are
what the rest of the post is about.

## How I look for knowledge

This is how I, as a person, deal with knowing things.

1. <span id="p1"></span>**I remember that a thing exists, not the thing.** I know the
   Postgres docs have a page about lock modes. I could not tell you what is on it. Most of
   what I "know" about a codebase works the same way.

2. <span id="p2"></span>**I ask the person who knows.** If someone wrote the auth module,
   I ask them before, or while, I read it. They have the context and they will answer with
   the nuance I would miss, or take a long time to get to by myself.

3. <span id="p3"></span>**I ask someone who was not there.** When I want a review I want
   someone who does not carry my assumptions or my bias.

4. <span id="p4"></span>**I go deep, then come back with a note.** When I write a query, I
   load the ORM, the database, the schema, the one weird thing about that table, all back
   into my head. When the query is written, that goes away. What stays is the query, and
   maybe a note like "this only works inside the transaction". Then I move on to the
   controller and load a different set of things.

5. <span id="p5"></span>**I keep two memories.** What I am holding right now, and what I
   know. The first one is tiny. The second one gets updated as a side effect of working,
   and things come out of it by association, without me searching.

6. <span id="p6"></span>**"Where was I?"** This is the one I think about the most. A
   teacher goes on a tangent, finishes it, says _"where was I?"_, and continues from
   before the tangent with only the point of the tangent kept. Nobody says "I am about to
   go on a tangent that will end in four minutes". You only know the tangent ended once it
   ended. I will call this the "where was I?" effect, for lack of a name I could find.

That is the shape of figure 1. The main thread is the task. The tangent is one of the deep
dives from [(4)](#p4): expand into everything relevant, produce something, come back. It
lands on the main thread a bit further along, and the thread continues carrying only what
the tangent produced.

The closest research I found to that shape is Event Segmentation Theory. Two short papers
cover it: Zacks and Swallow, [_Event Segmentation_][zs2007] (Current Directions in
Psychological Science, 2007), and Kurby and Zacks, [_Segmentation in the perception and
memory of events_][kz2008] (Trends in Cognitive Sciences, 2008). People chop continuous
activity into events without trying to. The boundary between two events is noticed when
prediction error spikes, which is to say after the next thing stopped being predictable.
At the boundary, the working model of the current event is updated and what just happened
gets encoded more strongly into long-term memory. Events nest, with small ones inside
bigger ones. And the boundaries people agree on tend to sit where a subgoal gets done.

Kurby and Zacks also cite studies where people who segmented finely recalled more detail
than people who segmented coarsely. That is a secondary result in their review, and if it
transfers at all it argues for small episodes over one big summary.

Two differences from what I am describing. Their work is about perceiving events, like
watching someone pitch a tent, and mine is about doing a task. And in their model the
boundary detection is automatic. _For an agent it has to be done on purpose, and the
harness has to ask for it._

## The same stream, two designs and the one I want

Take one sequence of messages: user asks for a feature, agent explores, agent writes a
query, agent runs the build loop, agent wires the frontend. Look at what happens to it
under three designs.

The first is a typical session: everything stays in order. The build logs sit between the
query and the frontend work for the rest of the session. Harnesses do keep some of the
recent conversation verbatim when they compact. OpenCode, for example, keeps the newest N
tokens next to the summary[^1]. But the main move is the same: when the window is nearly
full, summarize what is there into one block and continue. That summary is written over
the whole session at once, at a moment chosen by token count.

The second is the subagent: the build loop moves out of the main line. The main agent
writes a prompt, a fresh agent runs the loop and reports back one message. The main line
stays small and its prompt cache is never touched, which is a real win. The child starts
with the system prompt and the task, so it loses whatever the parent knew but did not
write down: which Node version the project wants, that the tests need a local service up,
that one package is pinned for a reason, all the small things the parent picked up while
reading around. What the child learned beyond its report sits in its own transcript. Some
harnesses keep that transcript and let the parent resume it, which is most of what I will
call `ask` later, but nothing makes the parent think to use it. And delegation only works
if the parent thought of it before starting, or I asked for it. If it ran the loop inline
because it did not expect seven long turns, the logs are in the session for good, short of
restarting from an earlier point.

The third is the tangent from figure 1. The same agent runs the build loop inline, with
what it already knew. When the build passes, the agent realizes the loop is done and folds
it: the main line continues from before the loop with a short note added, and the full
loop is kept somewhere reachable. It does not need to have predicted the loop. It only
needs to notice it ended.

  build logs stay and the context grows until one compaction drops it. Subagent: the main
  line stays small while a child climbs from its system prompt and task, and if the agent

</ThreeDesigns>

The numbered list maps onto this. Rows [(3)](#p3) and [(4)](#p4) are the ones I care about
most, because today they are one tool used for two opposite needs: one of them should
start with what the parent currently holds and fold back into it, the other should start
with less, on purpose. The section on forks goes into that split.

|what I do|what the agent does today|what a fold would add|
|-|-|-|
|[(1)](#p1) remember where, not what|shared memory files, AGENTS.md|a note plus an id that points back to the full thread|
|[(2)](#p2) ask the person who knows|explore subagent, grep the repo again|ask the thread that did the work|
|[(3)](#p3) ask someone not there|reviewer subagent|a separate agent, with less context on purpose|
|[(4)](#p4) go deep, come back|"run it in a subagent" (make it build)|the same agent expands, realizes it is done, folds|
|[(5)](#p5) two memories|the context window, for both|a small active context plus a reachable archive|
|[(6)](#p6) "where was I?"|compaction when the window fills|a fold when the episode ends|

Everything in that table is about one session. It is not a memory system across sessions,
people or machines, and it does not replace memory files or AGENTS.md, which are
cross-session, written on purpose, and usually committed. The archive in row (5) is the
opposite kind of thing: per session, written by the harness without anyone deciding to,
verbatim, and never meant for the repo. The memory file is my notes from the meeting. The
archive is the recording.

## Consolidate at the boundaries

The inference API keeps nothing between calls. The harness resends the message array every
turn, the weights stay fixed, and whatever the agent worked out exists only in that array
or in the side effects it caused, files it wrote being the common one. So the array is
both memories from [(5)](#p5) at once: the thing being held right now, and the only thing
the model reads. _Compaction rewrites it when it nears the limit, over the whole session,
which has nothing to do with when anything was learned._

After a build loop, the array holds every failed run and the reasoning behind each guess,
including the guesses that were wrong. What the next step needs is which guess was right,
what was changed because of it, and what is still unchecked. Compaction prompts ask for
roughly that kind of state[^1], and until they run, the logs are in the context on every
turn. The prompt cache makes that cheap in money: the provider keeps the computed state
for the prefix and does not process those tokens again. It does not take them out of the
context. Every new token the model produces still attends over all of them, at the cached
price.

What I want is for the array to be rewritten at the moments where my own working memory,
the human one, would be rewritten: when a local question gets answered or parked. I will
call that span of work an episode. It starts when a local question becomes active ("why
does the build fail?") and ends when the question is no longer what the next action is
about. Written out, with `B` for the context before the episode, `E` for the episode with
all its logs, and `A` for whatever comes after:

```
today:     B + E       + A
proposed:  B + fold(E) + A
```

The bet is that a `fold(E)` much smaller than `E` finishes the task about as well, and
hopefully better, because `A` is no longer reasoning over logs that have little to do with
it. `A` is not the same `A` in both lines, since a different context produces different
next steps. "About as well" is about the outcome.

### What goes in the note

Everything depends on what `fold(E)` contains. The note I would want:

- what changed (files, config, external state)
- what was learned that affects later work, including the caveats
- what was decided, and what was rejected
- what is still open
- where to look if any of this turns out to be insufficient

If that looks like a compaction prompt, it is. OpenCode's asks for objective, decisions,
work state, next move, relevant files and important context, and tells the model to keep
exact paths, symbols and error strings[^1]. The content is mostly right already. What is
wrong is the moment and the scope: over everything, when the window fills, instead of over
one episode, when it ends. The biggest change in this post is the agent realizing it can
fold, not the fold itself.

The caveats, the rejected alternatives, the open items and the pointer are the parts a
later step can catch on, so I will call those the hooks. They are also the parts that get
dropped first, because a summary that reads well tends to be a summary of conclusions. Say
the note says "the claim query works" and the truth was "the claim query works, but only
inside a transaction: `FOR UPDATE SKIP LOCKED` holds the row lock until commit, so outside
one two workers can claim the same job", and a later step moves the query somewhere else.
The archive has the detail. The agent will not go look, because its active memory says the
query works. The pointer does not help there. The caveat had to be in the note.

Most of the raw material for the note is already in the episode, in the agent's own
messages after each tool result. Those are usually the extraction: what the output meant,
what to try next. I would use them as input to the note, not as the note. They are
replies, so they lean on the output they reply to and stop making sense once it is gone,
and they are written mid-episode, so some hold guesses that were rejected a few rounds
later. The note restates the survivors so they stand on their own and quotes anything a
later step may need exactly, like an error string or a path. The figure below shows the
shape. The contents are placeholders, as in every figure in this post.

Altmann and Trafton, [_Memory for goals: an activation-based model_][at2002] (Cognitive
Science, 2002), models how people suspend a goal, do something else, and get back to it.
Three things from it that I am using as a checklist, not as a result about agents. A
suspended goal is only recovered through a cue. In their words:

> "Now what was I doing?" can only be answered by generating the right cue as a reminder.

The cue has to be encoded together with the goal, before the suspension. And it only works
if it is obvious and not shared with too many other goals. Those three are my paraphrase
of their model.

By that checklist, a todo list is a cue written before the work, so it holds what the
agent intended to do and not what it found, and it is one list for everything. A todo list
the agent keeps updating gets closer, and then it is the state file from the opening
again. An AGENTS.md is written with no goal in mind at all. A note written when the
episode ends, by the agent that did the work, about that work, is encoded with the thing
it is a cue for. That is the analogy. Their experiments are about people resuming a goal,
not about notes.

### You cannot name the span before it happens

The new part is in [(6)](#p6). You only know the tangent ended once it ended. Zacks and
Swallow describe something similar for perception: the boundary is detected after
prediction fails, not before.

To be precise about what is unknowable up front: the end condition is usually easy to name
before starting. "Until the build passes" is a fine end condition. What cannot be named
before the work is the span: which files it will touch, which earlier turns it will turn
out to depend on, and what it will reveal along the way. A subagent needs the span's
inputs, not its end condition, so the prompt that starts one is a bet, made before the
work, about what the span will need. The bet is often cheap and often right. When it is
wrong, the parent has under-briefed the child, which then either asks back or re-derives
things by globbing and reading what the parent already read, or it has delegated something
that was two lines of work.

Naming the span after the fact asks two things of the agent that did the work, since here
there is no child, only the main agent. First, to notice that the question is done: "the
build passes, and the next thing is not about the build". Then to say where the episode
started: at the first build run, not at the query that preceded it. The harness can mark
every turn for free, so the second one is a choice among existing marks, but it is still a
choice, and a wrong one either folds the query work into the build note or leaves half the
logs in place. The agent has to step out of the task for a moment, look at its own
context, and say which span is done. It breaks the fourth wall. In people that step is
automatic. In an agent it has to be done on purpose, and it is the new thing the harness
has to get from the model.

It is not the hardest thing, though. Noticing that the build passed is easy. Picking the
start is a choice among a handful of marks. The hard part is the note: deciding what a
step twenty turns from now will need, when nobody knows what that step is. The "query
works" case is that failure exactly, and no amount of boundary detection fixes it. So, two
separate problems: has the local activity ended, and what must survive it. The first is a
judgment the model has all the information for once it is asked. The second is partly
unknowable, which is why the archive, the hooks and the ways back exist at all.

How well a prompt gets the first one out of current models, I do not know yet. A system
prompt can describe the move and the test for it, and models already make an end-of-turn
decision and a tool-or-no-tool decision on every step, so "this episode is done" is the
same kind of decision. A model trained on it would be better at it, the way trained tool
calling beats prompted tool calling, and the harness produces training data for the second
problem on its own: every time a folded thread gets asked something the note should have
carried is an example of a note that was too thin, with the caveat that going back is
sometimes the right outcome and not a mistake. Prompting first, and training would make it
better.

The boundary is also only a cue, not a certification. Finishing one question can open two,
and something found late can revise an earlier conclusion. At the boundary the question to
ask is: can the next step proceed from `B + fold(E)`? If yes, fold. If not, the episode is
still open or the note is not good enough yet. That test only covers the next step. It
says nothing about the step twenty turns later, and in the "query works" case the honest
answer at the boundary is "I don't know", which is why the caveat has to be in the note
regardless.

### The note is lossy on purpose

The version of me that moves on from the SQL query does not carry the database docs with
me. What I object to is losing the detail irreversibly and then treating the summary as
the whole truth. So the full episode stays, somewhere the agent can get back to, and the
note ends with a handle that points at it. How going back works is
[its own section](#going-back).

That changes what counts as a failure. If the goal is a small active context plus a
reachable archive, the agent going back to the archive means the system is doing its job.
What I want low is

```
tokens carried per turn
+ cost of going back
+ mistakes from detail that was neither carried nor fetched
```

The units do not add, so treat it as a cache policy: fold finished episodes, fetch on
touch, and let the agent's judgment about what to keep sit on top of that.

### "Where was I?"

The teacher finishes the tangent and says it out loud. That is the moment I want the agent
to have. "The build passes. Where was I?" The agent names the span and writes the note:

```
fold(since: "t4", note: "...")   -> "b2e4"
```

The harness truncates the view back to before `t4`, appends the note with the handle, and
files the span under `b2e4`. The part of the context before the span was already there, so
getting back to the main line costs no new tokens, and it stays a cache hit as long as the
cache is still alive[^2]. The price is in noticing, in choosing `since`, and in the note.

  handle b2e4, followed by the user's message from inside the span, kept verbatim.
  Everything before the chosen turn stays a cached prefix, and the new block is a fresh
  write. A second pass compares a note that says "the claim query works" with one that
  keeps the caveat about the transaction, when a later step moves the query.
</Fold>

## Handoff is broken, and fork is the first step

Back to the subagent prompt with little in it. I mean the kind of subagent that continues
the parent's own work, like "make it build". Reviewers are a different case and get their
own section below. The parent is asked to produce, before the work, a written version of
what the child will need. The goal exists at that point. What does not exist yet is the
span, so the prompt is a guess at its inputs. And the parent is badly placed to write it:
what it knows is not sitting in one place it could copy from, it is spread across a few
hundred messages as things it noticed along the way, so to write the prompt it would have
to first reconstruct its own understanding.

The fix for that specific problem is small: do not write a prompt, fork.

```
fork(task)   -> result, handle
```

Take the parent's message array as it is, close the open tool call with the task as its
result, run the child to completion, and return its final message to the parent. The child
starts with what the parent holds because it starts as the parent. There is no prompt to
write. The prefix is byte-identical to the parent's, so it is a prompt cache hit on every
child turn. This is not the "branch this conversation" button in chat apps, which copies
the conversation and leaves you with two of them. Here the copy exists to come back.

A clean subagent is cheaper per turn, since it carries a 15K system prompt instead of the
parent's prefix. What it pays instead is redoing the parent's reading, and what nobody can
put in a table is whether it ends up with the same result. The table below is an
illustrative cost model for the token side only. The figures show one short loop, and cost
only matters in a long session, so it assumes a parent prefix of 100K tokens, a loop of 30
turns that grows the context by 150K, cached reads at a tenth of the fresh price and
writes at 1.25x, and that the clean child re-reads about 30K of what the parent had
already read, written once and then re-read on every later turn. The rate column is the
price each row is billed at, as a multiple of the fresh input price, and the token columns
are after that rate is applied: the fork's prefix is 3M raw tokens over the loop, read
from cache, so it costs what 300K fresh tokens would. The first turn of each child, which
is a write, is left out.

|cost|rate|fork|clean subagent|
|-|-|-|-|
|prefix, read from cache on every turn|0.1x|300K|45K|
|loop growth, written once|1.25x|188K|188K|
|loop growth, read from cache as it grows|0.1x|225K|225K|
|re-reading what the parent had read|1.25x once, then 0.1x|0|~125K|
|total, in fresh-token equivalents||~713K|~583K|
|in dollars, at $3 per million fresh tokens||~$2.14|~$1.75|

The conclusion I take from it is narrow: the prefix row alone suggests a 7x gap, and the
loop's own growth, which both pay, brings it to about 1.2x, or 1.6x if the child does not
need to re-read anything. Under these assumptions continuity costs a moderate premium.
Whether the clean child's result is as good, and whether it takes the same number of
turns, is what the table cannot say. The premium widens as the session gets longer, and it
shrinks as cached reads get cheaper: a tenth of the fresh price is the common rate today,
and the newest models on both big providers are already at a twentieth or less[^2]. If the
parent sat idle past the cache lifetime, the first child turn is a full write of the
prefix.

The same prefix is also the strongest objection to the idea. If bloat hurts reasoning, why
hand the child the query work and every stale guess the parent made along the way? That is
the actual reason "run it in a subagent" works today, and the child inherits the parent's
wrong guesses together with its right ones, and will anchor on them the same way the
parent did.

My answer is that the fork should inherit the parent's view, meaning the context as it
stands after earlier folds, rather than the raw log. In a harness that folds, the query
episode is already a note by the time the build starts, so the fork inherits the note and
the stale guesses from that episode are gone. That covers closed episodes. Whatever is
still open is inherited as is. It also changes the table: with the query work folded, the
prefix in that model drops from 100K to about 40K, and the fork's total lands around 533K,
below the clean child. Until folding exists, a fork inherits the raw log and pays for
continuity, which is fine for a long loop and wasteful for a short lookup. Short lookups
should keep a clean child. So the two pieces depend on each other: fork fixes the handoff,
folding makes fork affordable.

Fork and the fold end in the same place: a main line that grew by one block, an archived
span, and the same question about what the block should say. They differ in when the
decision is made and how many. Fork decides before the work and only has to decide "this
is separate", since the start is fixed by construction. The fold decides after, and has to
pick both the end and the start. A fork's transcript is separate from the parent's, so
several can run at once as long as their edits do not collide, because the files are still
shared. And in the simplest scheduling the user can keep talking to the main line during a
fold but not during a fork, though that is a harness choice rather than something
inherent. The fold is closer to how I think it should work and it needs the judgment from
the previous section. Fork needs no new judgment from the model, and the fold reuses its
archive, its handle and its note format.

  decides after, choosing where it started. Both re-read the parent prefix at the cached
  price, about 713K tokens over 30 turns against 583K for a clean subagent that has to
  re-read what the parent already knew. With the parent already folded, fork and fold drop
  to about 533K, below the clean subagent.
</ForkVsFold>

### Forks and other agents

Once fork exists, which subagents should become forks? Not the reviewer. That is
[(3)](#p3), and the reviewer is useful because it does not carry assumptions or biases.

If "sub-agent" meant a piece of the main agent, today's subagents would not qualify: they
start with only what the parent wrote into the prompt. What they are is other agents
handed the wrong prompt. So two kinds. A fork is a piece of the same agent: exploration,
"make it build", splitting a task into parts. It starts from the parent's view and folds
back. An other agent is a second one consulted on purpose: review, a second opinion,
anything where **independence is the point.** It starts with less. Not with nothing,
because a reviewer that does not know the constraint I gave at the start will miss it. The
useful split is to hand it the user's messages and withhold the agent's conclusions. A
reviewer that receives the parent's reasoning for why the diff is correct will mostly
agree with it. It is the same model with the same blind spots, so this is a weaker version
of a second opinion than a human colleague is, but it is the version available.

Most harnesses today run both kinds through one mechanism. Forks start empty when they
should inherit, and reviewers sometimes get handed the parent's reasoning when they should
not.

<ForkVsOtherAgent>
  Two sessions. A fork starts with the parent's whole view and its result merges into the
  main line. A reviewer gets the user's messages and the diff but not the agent's
  reasoning, and finds that the claim query runs outside a transaction. Handed the
  reasoning, it agrees the diff looks good.
</ForkVsOtherAgent>

## Going back

Folding is half of it. The other half is what happens when the note turns out to be
insufficient, which it will be sometimes, because it was written without knowing every
later step. What survives a fold is the note and a handle, and going back through the
handle has two shapes. I would try the cheap one first.

```
recall(query)          -> matching lines, each with the thread it came from
ask(handle, question)  -> one answer from that thread
```

`recall` is search over the archive with no model call: the exact error from a specific
round, or where a function was defined. Plain grep gets most of it, and a ranked search
(BM25 or embeddings) helps when the agent remembers the idea but not the exact string. It
searches everything the thread held, the tool outputs and the agent's own messages and the
reasoning where the provider returns it, not only the final report or the files it
touched. It is cheap, I expect it to cover a lot of what comes up, and it only works when
the agent already knows roughly what to look for.

`ask` is for judgments: why did we fix it this way and not the other way. The archived
span is a context that still exists. Append the question to `B + E`, run one step, return
the answer. The span never re-enters the main line. The request keeps the same tools block
as the original thread, since swapping it would miss the cache, and the thread is told to
answer without acting. If it needs to read something new to answer, that is a fork, not an
ask. This is [(2)](#p2), with one honesty note: it is the same model re-reading its own
transcript, so it is closer to that person's notes than to the person.

An `ask` re-reads `B + E` at the cached price if the cache is still alive and at close to
full price otherwise[^2]. Going back usually happens later than the cache lifetime, so
full price is probably the common case today. If sessions started asking their own
archives often, that is the kind of pattern providers price for, and the cache section at
the end says what would have to change.

<GoingBack>
  Two tool calls from the main thread. `recall("TS2322")` returns matching lines from
  archived thread b2e4, including the tool output, the agent's own message and a line of
  reasoning where the provider returns it, with no inference. `ask("b2e4", "why regenerate
  instead of fixing the type in api.ts?")` loads that thread off the main line, appends
  the question, and returns one answer: api.ts is generated from the OpenAPI spec, so a
  hand edit is overwritten on the next generate. Only the answer enters the main line, and
  its cost depends on whether the cache is still warm.
</GoingBack>

Folds nest, in one direction. A fork can fold inside itself, so an archived fork can
contain its own notes and archived spans, and the archive ends up as a tree. A fold on the
main line does not reach behind an earlier note, so notes on the same line never contain
each other. The agent should not have to know any of that. It searches by keyword, not by
thread, so `recall` runs over every archived span flat and reports which thread each line
came from, and `ask` takes any handle, however deep.

The case I have least for is when the agent does not know it needs to go back. The note
said the query works, nothing in the main line says otherwise, and the step that will
break is three turns away. A few defenses, from cheapest up:

- The caveat in the note. First line of defense and the weakest one, since caveats are
  what gets dropped.
- Habit. The system prompt says that folded threads exist, that `recall` is cheap, and
  that an unknown which an earlier thread might have known is worth one `recall` before
  guessing. The model gets used to calling it the way it gets used to reading a file
  before editing it.
- File touch. Each archived span's index lists the files and symbols it touched. When the
  agent touches one of them again, the harness surfaces that span's note.
- Overlap. Match the recent context against the archive every turn and inject "possibly
  relevant: thread X" on overlap. The noisy one.
- Me. In an interactive session I notice when something looks wrong and ask. That only
  helps once it already looks wrong.
- Training. Going back when the note is thin is a habit, and habits are what fine-tuning
  is good at, the same way tool calling went from prompted to trained. The archive and the
  asks a harness records are the data for it.

What comes back is also what was observed then. Reasoning was conditioned on observations,
so if the file changed, "we ruled that out" may not hold anymore either. The index can
store a hash of each touched file at the time, and when a span is asked or recalled the
harness can prepend which of them changed since.

## Putting it together

The moves above need names to be talked about, so for this post they are `fork`, `fold`,
`recall` and `ask`, over this little data model:

|name|what it is|
|-|-|
|log|one append-only message list per thread: the main line and every fork|
|view|what the model sees: the main log with folded spans replaced by their notes|
|archive|the logs of folded spans and finished forks, with an index of the files and symbols each touched|
|handle|the id of an archived span|

A few constraints fall out of the argument rather than out of taste:

- `since` is a turn id the model can see in its view, not a hidden checkpoint. The harness
  stamps one on each user message and tool result as it writes them, never after the fact,
  so the stamps never change bytes that are already cached. It snaps `since` to the turn
  boundary and refuses one that reaches behind an earlier note.
- The note follows the template from above (changed, learned with caveats, decided and
  rejected, open, where to look) and the harness appends the handle.
- User messages inside a folded span stay on the main line as written, next to the note,
  with the turn they were said at, so a correction given mid-episode does not read as a
  new instruction. Large pastes get a size cap and a pointer. The note must not be allowed
  to rewrite what I said.
- What changed on disk comes from diffing the working tree between `since` and the fold,
  not from the model classifying its own commands.
- The archive is written before the view drops the span.
- `fold` can also be triggered by the user with a slash command. That is the same move
  without the noticing step, and it is the way to find out whether the note template holds
  up before asking the model to notice anything.

## Cache

Everything above assumes prompt caching keeps working, because without it the cost goes
through the roof. Prompt caching matches the longest prefix of the request that the
provider has seen recently. Both big providers now offer roughly the same two modes: an
automatic one, where the breakpoint follows the end of each request, and an explicit one,
where you place up to four breakpoints yourself and an entry is written at each[^2]. A
harness checkpoint, the per-turn mark used for `since`, is a position in the log and is
not a cache breakpoint. The harness has to put a breakpoint at a checkpoint on purpose if
it wants a hit there.

|operation|what changes|cache|
|-|-|-|
|append|a new tail (tool result, fork return, recall result)|hit on everything before it, the tail is written|
|fork|the parent's prefix plus the task|hit on the prefix if an entry sits at its end. If none does yet, forks started together each write it, since an entry only exists once a response has begun|
|fold (latest span)|truncate to `since`, append the note|hit on the prefix if an entry was written at `since` and is still alive, the note is written|
|fold deferred to compaction|everything after an old position|rewritten, once, together with the rest|
|ask|branch from the archive point|hit on `B + E` if an entry sits there and is still alive, else `E` is rewritten (`B` is shared with the live main line)|

What falls out of that:

1. `tools` and `system` are frozen for the session. On Anthropic they sit before the
   messages in the cached prefix, so a change to `tools` rewrites everything and a change
   to `system` rewrites everything after it, and OpenAI lists `tools` among the settings
   that break the prefix too. Anything dynamic goes in a trailing block after the last
   breakpoint. It is billed uncached every turn, so keep it small.
2. Fork instructions go in the task message, not the system prompt.
3. Keep one breakpoint at the start of the open episode. With a single breakpoint at the
   end, each request only reads and refreshes the longest entry that matches, so during a
   long loop the entry at `since` is never read again and expires before the fold. A
   second breakpoint at `since` makes every request check that position too, which keeps
   the entry alive. Without it the fold is a full write of `B`.
4. `fold` only reaches back to `since`, so folding an older span is not an operation it
   has. The natural time to clean up older material is the next full compaction, when
   everything is being rewritten anyway.

The lifetime is the part that matters here. Anthropic's default is five minutes from the
start of the last request that used the entry, with an hour at a higher write price.
OpenAI's newest models default to thirty minutes, and some older ones can keep entries for
up to a day[^2]. A session that keeps moving needs no more than the default, since the
next turn comes within seconds. A harness that asks old threads questions does need more,
and lifetimes have been getting longer on their own, so I would expect that to keep
happening. Cheaper cached reads help too, and those have been dropping as well.

## Try it today

I built this as a package for [pi](https://github.com/earendil-works/pi), so the post has
something to point at: [pi-episodes](https://github.com/arthurfiorette/pi-episodes).

```sh
pi install npm:pi-episodes
```

It adds the four tools from above, with these names, and a short system prompt section
that tells the model when to use them. Stamps go on every user message and tool result as
they are saved.

- `fold` removes a stamped span from the model's context and leaves the note in its place.
  Pi's own compaction stays on as a fallback.
- `recall` searches folds, forks and compacted turns with no model call, ranked, with
  exact and regex modes.
- `ask` resumes a folded or forked thread for one question.
- `fork` runs a copy of the agent with its current context and tools.

Around them: a working tree diff per fold so the note lists what changed on disk, a
file-touch cue that names the archived thread when the agent reads or edits a file that
thread touched, a staleness line on `recall` and `ask` listing the files that changed
since, and a reminder of open items after a fold. `/fold` folds by hand, which is the
smallest experiment I would run first: fold after a real build loop, then give the agent a
task that depends on something inside the fold, and watch what it does with the note.

What it is meant to find out is the list I would have put here as open questions:

- whether the model notices an episode ended and picks where it started, without being
  told
- whether its notes keep the caveats, or fail the "query works" way
- whether it goes back to the archive when it should, and whether the file-touch cue helps
  or adds noise
- whether a fork anchors on the parent's wrong guesses more than a clean subagent would
- whether a smaller, state-shaped context makes the main line reason better at all, or
  that is an intuition left over from when windows were small

The repository has a measurement plan for those. I am working through it, and I will come
back here with what it says. But I would rather hear how it feels to work with after a
week than publish a benchmark I vibed into existence, so if you try it, tell me what the
agent did with the notes. The shape still feels right to me, and now I know part of it has
a name.
